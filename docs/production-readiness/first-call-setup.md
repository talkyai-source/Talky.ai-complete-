# First authorized call using the existing screens

This is the supported setup order for the local production-readiness candidate. It is a guide for designated acceptance testing, not evidence that a new customer has completed it. The deployment, approved model/voice, knowledge, trunk, caller ID, connector accounts and owned test destination must be recorded before a telephone test.

1. **Create and verify the account.** Use `/auth/register` and its email-code steps. Sign in through `/auth/login`. Confirm the correct account and tenant. An incorrect password is a sign-in error; an existing signup email should offer sign-in or another email address. If account verification is unavailable, resolve that error before proceeding.
2. **Check the purchased entitlement.** Use `/billing/plans` and `/billing` to inspect the supported offer and the saved subscription state. Returning from a checkout page alone does not prove activation. A default plan or a visible minutes number does not prove that a new call is authorized.
3. **Set up the telephone route.** In `/settings`, use the telephony and SIP trunk controls. Select the intended provider/trunk and caller ID and inspect its current readiness. Where caller-ID ownership verification is not available in the UI, the operator must complete the existing backend provisioning and document the ownership evidence. A seeded trunk, saved settings or an old successful test is not current route readiness.
4. **Save the intended agent.** In `/ai-options`, save the approved model, voice, persona and applicable controls. Reload to confirm the saved selection, then assign that profile to the campaign. Traditional speech providers and native Realtime retain their separate configuration contracts. A visible model option is not proof of live provider availability.
5. **Prepare the campaign knowledge.** Use `/campaigns/new` and the Basics, Knowledge and Review steps, then the campaign's Knowledge panel. Confirm the intended current documents and review representative answers, including questions the documents cannot answer. Resolve unsupported claims or missing facts before a customer-facing call.
6. **Add a permitted test contact.** Use `/contacts` and attach the intended list to the campaign. Use only the designated, owned or explicitly authorized destination. Check the destination, region and consent requirements. Staff access currently uses existing administrator-assisted account/membership operations; an email invitation-and-acceptance journey has not been demonstrated and must not be promised.
7. **Read the campaign's readiness result.** The campaign start control uses the shared backend readiness check. Resolve its specific blocked reason before starting. The browser “Test agent” microphone session is useful for checking interaction, but it does not verify telephone routing, the displayed caller ID or carrier behavior.
8. **Make the explicitly authorized telephone test and inspect the result.** Verify the received caller ID, opening, comprehension, interruptions, grounded answers and unhurried closure. Check the call record and Leads section for the actual transcript, contact evidence, outcome and any action receipts. “Accepted,” “queued” and “unknown” outcomes are not completed external actions. Keep uncertain results for review rather than resubmitting an action with a new identity.

If recovery is needed, use the existing password-reset, MFA/passkey and Security session controls. A sign-out warning means the browser cleared its local state but server revocation is unconfirmed; sign in again and review other sessions. Do not report a reset email as delivered without delivery evidence.

## Operator prerequisites and open acceptance

- Production must point the existing `NEXT_PUBLIC_API_BASE_URL` at the canonical backend. The local Next API compatibility routes do not provide a second production identity authority. Ship the matching backend, frontend and required database migration together.
- Confirm current verification and membership evidence for existing accounts. Do not infer email verification or grant a role merely to get an old account past the checks. No undisclosed database edits belong in a customer setup procedure.
- The designated inbox/device recovery tests, invitation requirement, first owned-number call, five-user usability proposal and released configuration remain open until their actual evidence is recorded. This guide does not close those gates.
