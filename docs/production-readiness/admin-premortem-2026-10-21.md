## Why these failures can recur

1. Some Admin endpoints reconstruct operational state independently of the real health and execution paths. Fixed demonstration values survived beside genuine instrumentation.
2. The database adapter returns an error field for some failures. Callers that only catch exceptions can mistake failed reads for empty data and failed writes for success.
3. Multi-step changes lack a shared transaction or a stale-operation check. A later response can overwrite a newer administrative decision.
4. Admin implements only part of the canonical identity contract. MFA, refresh, cross-tab ownership and navigation permissions disagree with working backend capabilities.
5. Tests cover important isolated behavior, but cannot establish deployed configuration, real persistence/concurrency, provider effects or operator acceptance.
6. Resource ownership is applied inconsistently. Some newer views retire old requests correctly, while media, list filters and polls can install a response belonging to a previous selection or session.
7. HTTP status is sometimes substituted for business outcome. A refresh can erase a mutation failure, or a non-2xx response carrying a durable pending receipt can be turned into a definite failure. The deeper action-drawer review also found the inverse: a confirmed cancellation receipt is discarded when its follow-up read fails.
8. Some backend promises had no complete producing, scheduling or evidence path. Provider observations, bounded expiry, original-PBX enforcement, formal hold/appeal frontend and bounded per-dimension enforcement projection now have local implementation evidence. Historical ownership, complete fleet coverage and hosted effect acceptance remain open; supplier-cost totals still lack an authoritative retained source. Changing labels or adding a database table alone cannot complete those functions.
9. A durable database decision does not guarantee a usable recovery journey. The Inbound baseline could save approval while hiding the request, and a stale pending request had no supported exit. Each existing operation needs discoverable saved state and a valid way to retire obsolete work; local browser keys alone cannot provide that after a reload.
10. Passing an isolated dialog test does not prove usability after real state changes. List refresh can remove the focus-return button, and error/confirmation text can push controls outside a fixed viewport. Test the changed screen after mutation, failed read and recovery, with actual keyboard and pointer interaction.
11. The Vite Admin and Next Admin surfaces have independently maintained API assumptions. The Next partner directory was absent, an early permissive schema branch discarded returned metadata, and the audit/security console paths and shapes disagree with the mounted APIs. Some mock tests repeat the client's incorrect route/envelope assumption, so a passing test can confirm the same mistake twice. Compilation cannot detect an unexercised HTTP contract. The separate Next audit page already uses the canonical path; reuse the existing contract rather than creating a third service or a success alias.
12. Role labels, supported permission names and data scope are separate contracts. The Next console advertises partner-admin audit/security access, while the checked permission strings are absent from the canonical enum used to decode grants. The canonical audit/security scope also admits cross-tenant requests only for a platform administrator. These source findings predict refusal, not a demonstrated data leak. Prove normal-auth role behavior and settle the intended existing policy before changing permissions; do not manufacture partner-wide visibility with a client filter.
13. Ordinary access blocks and formal holds previously wrote the same profile flag without preserving separate decision ownership. A correctly serialized later restoration could therefore undo another saved decision. New supported conflicting writes are now guarded, but historical ambiguity and incompatible deployed writers remain a release concern. More locking alone would not recover the missing intent.

These findings identify code and contract causes. They do not establish that every defect caused a customer incident, or identify which person or coding tool introduced it. Baseline reproductions and repaired-candidate checks are kept separately for that reason.

The corrective principle is to reuse existing authoritative paths and make their results explicit. Do not create a general workflow engine, replace the database adapter globally or rewrite the frontend.
