## Root causes and bounded repairs

1. **Approval did not identify the connected account.** Email and calendar previews could retain the content while reconnecting changed the external account behind the same connector row. Trusted server-only review metadata now freezes the connector, provider and external account. Apply checks that identity, including after a definite authentication rejection and token refresh. Calendar changes additionally bind the reviewed event and its attendees, content and state. Historical events without original-account proof remain unavailable for assistant mutation. Model-supplied review markers, including nested plan arguments, are stripped. Support-report sender selection is also frozen at preview; an approved tenant account cannot silently become the configured SMTP sender.

2. **Losing the Apply response lost the usable action reference.** Both dashboard text and voice sockets now recover the original actor-owned, tenant-owned durable receipt. `proposal_status` reads that same record without execution. Repeated Apply after the process-local proposal is consumed also performs a receipt lookup; it does not create another action key. Running and unknown effects stay held. A missing record reports unavailable evidence instead of instructing the customer to send again. Inner action references survive the outer executor's receipt assignment.

3. **The Actions page called nonexistent workflow endpoints and misread the real actions endpoint as a catalog.** It now reads the real paginated action records, filters them through the supported API, and presents saved status, account and provider references. The existing Assistant preview/Apply journey remains the execution path. Unsupported generic plan/execute/retry clients and manual verification checkboxes were removed. Export explicitly covers the current page. Status checks are read-only in both assistant modes. The Leads view likewise exposes each CRM destination's original references separately, without raw request content.

4. **A completed row was being treated as proof of delivery.** Durable state and explicit confirmation evidence are separate. Missing or false confirmation proof does not become positive merely because the row says completed. Email provider acceptance is labeled acceptance; a callback handed to the queue is labeled queued for calling, not a completed call. Scheduled reminders retain their saved reminder reference; scheduling does not prove later delivery. Receipts use a bounded allowlist and omit credentials, bodies and raw provider payloads.

5. **Cancellation could race dispatch, and generic retry acknowledged work with no consumer.** Admin cancellation and callback preparation now share the authoritative action-row lock. A callback's deterministic job identity is saved in the same transaction that reserves the job, before queue handoff. Cancellation after that point returns a conflict. An unclaimed durable execution receipt can cancel; a legacy pending audit cannot prove that its underlying work stopped. Tenant and partner admins remain scoped to their authenticated tenant. Unsupported generic retry returns an explicit 501 saying no action was queued. That is correction of a false acknowledgment, not completion of a retry workflow. [Detailed reproduction and boundary evidence](2026-10-05-ag06-admin-actions.md).

6. **CRM retries could use changed contact details or a stale summary.** CRM preparation now uses the shared current contact-evidence projection and the current transcript/summary digest. Explicit pending, withdrawn or revised primary contact evidence suppresses an older imported value. The strongest same-lead manual review takes precedence. Additional contacts are not silently promoted to primary. Migration `0058_crm_contact_effect` preserves the original prepared contact arguments, source versions, account, recipient and digest before contact creation. This evidence is private storage, not a public payload dump.

7. **An uncertain CRM create could adopt the wrong search result.** An unknown contact creation remains held in its original account, retaining the original intent. A changed recipient or an immediately empty search does not prove nonexecution. A known definite rejection may retry only the same contact intent; unrelated call metadata changes do not permanently invalidate that safe retry. Changed creation arguments or contact authority still block it. Existing call-reference reconciliation stays bound to the original account. Independent provider receipts retain independent results.

8. **Sequential checks left an await window before the CRM write.** The final admission check compares a bounded database snapshot before and after the source reads: call and lead revisions, current primary evidence and winning manual corrections, connector settings and the resolver's authoritative active account. Insertions, deletions, withdrawals and account changes during validation stop the write. Token-only refresh does not. The last database snapshot defines admission; a change committed after that point cannot atomically cancel an operation sent to another system.

## Remaining acceptance and rollback

Designated accounts and recipients still need to demonstrate each sold email/calendar/CRM action and original-account readback. The existing CRM contract has no provider-neutral explicit contact-ID readback, so uncertain contact creation remains unresolved for support review. Generic Admin retry and an audited operator resolution mutation are not claimed implemented by the 501 response or by adding a visible receipt. A support owner must establish authoritative outcome evidence before any newly reviewed action; a timeout, empty search or model judgment is insufficient.

Pending proposal previews remain process-local. A preview lost before a durable claim is not reconstructable as approved work. Previously admitted effects cannot be undone by a later correction or by reverting code. Preserve original payload/account evidence, running/unknown/completed receipts and deterministic callback job identities. Do not reset idempotency or replay a queue on rollback.

Apply the additive migration before code that reads the contact-effect column. Its downgrade refuses to destroy the preserved evidence. The original prepared arguments can contain existing CRM contact details and a bounded call description, so they retain the protection and retention obligations of the source CRM delivery record; only references and digest are projected to the customer UI. Production migration, retention and rollback exercises remain part of release acceptance.
