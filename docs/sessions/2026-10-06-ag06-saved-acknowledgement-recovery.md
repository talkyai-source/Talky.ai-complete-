# AG06 — recover an already-saved Gmail acknowledgement

This bounded change repairs one existing failure: Gmail and the inner email service acknowledged acceptance, but the outer durable executor failed its first final local save and subsequently saved an `unknown` envelope containing that original successful result. It adds an explicit platform-admin review on the existing action detail. It does not send, retry, inspect a provider, load credentials, infer a missing child, or treat provider observation as completion.

The supported record is a canonical outer `send_email` action from the dashboard or voice executor, still `unknown`, with the complete original `authorization_row_v1`, message ID, distinct saved child action ID, literal success/confirmation flags and the appropriate saved acceptance status in one nested result. The server checks the outer action identity, tenant, exact original executor request hash, saved proposal/voice request identity and original proof correspondence. Dashboard recipients must match the frozen request. Voice admission also checks the saved call's tenant/campaign and any recorded lead relationship. This relationship check is historical ownership evidence; it does not prove that an email's contents were correct or that the caller understood a confirmation.

Missing, conflicting, malformed, legacy, running, bulk, form, SMTP, CRM and calendar acknowledgements remain unsupported. A provider ID or an inconclusive read can never qualify. The current connected account is irrelevant to recovery of an already-recorded acknowledgement; no current account or refreshed token substitutes for historical proof.

`POST /admin/actions/{action_id}/recover-acknowledgement` accepts only a fresh review request UUID, the source digest shown by action detail and a bounded reason. The current authenticated session and canonical active/verified platform-admin profile are checked in the database transaction, including after acquiring the action row lock. Tenant and partner admins have no recovery capability. The transaction appends the original uncertain output/timestamps and actor/reason to an immutable resolution record, then restores the already-saved result and changes only the outer status/output. Both writes roll back together. The original input, idempotency key, actor/linkage and recorded times stay intact; the separate audit time is the recovery time, never a newly invented email send time.

The same actor/request/action/source digest/reason replays the same recorded recovery, including concurrent requests or a lost response. A different body using that request ID is rejected. Normal durable executor replay reads the saved result without dispatching another effect. The UI uses explicit confirmation, keeps an uncertain request's UUID and body for a safe manual repeat and refreshes the whole selected drawer after acknowledgement.

The source digest normalizes only known row UUID and aware timestamp columns, so adapter strings and native PostgreSQL scalars agree. Nested JSON payload and reference strings remain unchanged. The existing executor's request hash serialization remains separate and retains its original ASCII escaping behavior.

## Migration and retention boundary

Additive migration `0062_saved_acknowledgement` adds `assistant_action_resolutions` and the one composite parent key required for its tenant/action foreign key. There is no backfill, automatic status repair or provider write. Forced row security requires a current active/verified platform profile and binds inserted actor identity to the transaction's current user; worker RLS bypass alone is insufficient. UPDATE/DELETE are denied and an append-only trigger provides an additional mutation fence. Actor UUID/role are snapshots without a user foreign key, preserving existing user deletion behavior.

The resolution foreign key deliberately restricts SQL deletion of a recovered action and a cascading hard deletion of its tenant. Repository inspection found no supported action hard-delete route; the existing tenant archive only changes subscription state, and the cleanup worker targets call/stream events. This is an explicit new evidence-retention boundary, **not privacy/deletion acceptance**. A destructive downgrade is refused; retention changes need a separately reviewed forward migration. Existing broader deletion/retention acceptance remains unresolved.

It never alters public data/schema or calls a provider.
