## Root causes and repairs

1. **Different entry points disagreed about who still had access.** Cookie authentication could accept a revoked session that bearer authentication rejected. Stale profile roles could survive changed or removed membership. One shared principal lookup now checks the persisted session, active verified profile and current tenant membership. Explicit platform-admin policy is preserved. Direct grants require eligible membership; tenant queries and role edits enforce the authenticated tenant and both existing/requested role ceilings. Text and voice assistant sockets recheck authority on admission and subsequent messages; tools check again before effects. Campaign test sockets use the same principal and retain their periodic revocation monitor.

2. **Delayed requests could use the next person's login.** The HTTP client freezes the verified user, tenant, token and identity generation for each request. Refresh, intercepted responses and delayed body reads cannot retry as, install results into, or clear a newer identity. Optional expected-user/tenant headers are consistency checks after authentication, never a way to select authority. Refresh returns its current principal and access token. Protected work is withheld until the identity is verified. A shared token writer fixes the real callback sequence where a newly installed token was invisible to an already-mounted AuthProvider. Cross-tab changes immediately invalidate local identity and caches while the canonical profile reloads.

3. **Logout could claim success or affect another login.** The API no longer treats missing logout endpoints as successful revocation. Both logout controls use AuthContext's server-confirmed/current-identity result. A late logout does not clear or navigate a newer account. An uncertain current logout clears local state and displays a warning; it is not automatically replayed on the next login. Revoking other sessions reports confirmed and unconfirmed counts instead of swallowing failures.

4. **Next's compatibility API was another production identity authority.** Auth and profile compatibility routes now return an explicit unavailable response before reading credentials or touching legacy storage. The remaining compatibility catchall is also unavailable in production; its separate legacy session table cannot authorize production writes. Server rendering and proxy role checks use configured canonical `/auth/me` without caching or alternate `/me` fallback. Configure the existing `NEXT_PUBLIC_API_BASE_URL`. This is containment of an unsafe fallback, not completion of every compatibility feature.

5. **Account creation and role changes could leave unusable or misleading records.** The legacy single-step register route is explicitly retired in favor of verified signup. Canonical signup, membership and session issuance are transactional. Known rejected-login counters persist, while unexpected issuance failures roll back partial sessions. Authorized Admin creation now creates the canonical active membership atomically; role edits update that membership or report the missing historical link. Admin list/detail/filter and UI distinguish stored assignments from effective access. No verification or membership is invented for legacy accounts. Duplicate-signup wording remains specific to signup; wrong-password login remains a credential error.

6. **One-time credentials were not always one-time or atomic.** Passkey challenge consumption checks affected rows, binds registration to its owner and serializes credential counters. The real verifier enforces the already-requested user-verification requirement. Browser components preserve server RP, challenge, allowed/excluded credentials and authenticator settings. MFA challenge/factor consumption and session issuance share a transaction; failed attempts persist. TOTP stores the accepted time-step counter, preventing replay across a clock-skew window. Pending setup cannot disable a concurrently confirmed factor. Recovery-code replacement is atomic. Password reset checks a private password-generation digest under a user-row lock, so a committed reset invalidates the old code even if Redis cleanup fails. Cleanup cannot delete a newer request. Generic responses do not claim unconfirmed email delivery.

7. **Existing runtime fields were missing from the migration chain.** Migration `0059_auth_identity_contract` and the bootstrap schema define verification evidence and bounded MFA attempts. Missing verification defaults false; existing correct values remain. Inconsistent historical data intentionally fails constraint validation rather than being silently certified. The migration uses a short lock timeout and a data-retaining downgrade.

The [first-call setup guide](../production-readiness/first-call-setup.md) orders the existing screens and names the operator prerequisites. The repository's staff invitation-and-acceptance journey is absent. Existing administrator-assisted setup is documented honestly; it does not close the invitation requirement.

## Remaining acceptance and rollout limits

Designated accounts, inboxes, devices, multiple tabs and the released frontend/backend pair must still demonstrate recovery and revocation. Browser-applied late `Set-Cookie` responses cannot be compare-and-swapped by this JavaScript guard; this remains an explicit cross-tab acceptance limitation. Checks occur at admission/message/effect boundaries, not every audio byte. A revocation committed after an external operation was admitted cannot undo that operation; durable unknown-result handling remains necessary.

Ship the compatible frontend/backend and migration together. Reconcile historical verification/membership evidence before release; do not automatically verify users, revive revoked sessions or restore the legacy register path. Legacy refresh families without valid bound sessions and pending reset records without the new generation proof require a fresh login/reset request. Preserve existing verification, factor and revocation evidence during rollback. No live deployment, provider call, staff invitation, first-buyer telephone journey, five-user usability result or final release gate is claimed by this checkpoint.
