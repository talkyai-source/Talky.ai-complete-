## 1. High priority: shared database helper corrupts SQL parameters

**Confirmed by production log, database state, source, and a failing reproduction.**

On 15 September at 18:24:14 UTC, the dialer logged:

```text
Failed to update job status: could not determine data type of parameter $10
dialer_origination_result_unknown ... same_attempt_redeferred=True state_recorded=False
```

The corresponding call beginning `bb8e6dc2` finished with 193 seconds of duration. Its job remained `retry_scheduled`, with `last_error=tenant_gap`, no final outcome and no completion time. The call records attempt 2; the job records attempt 1.

Root cause chain:

1. `backend/app/workers/dialer_worker.py:2478` builds a six-column update after origination.
2. The WHERE clause has four ownership parameters: job, tenant, campaign, lead.
3. `backend/app/core/db.py:412` shifts parameter numbers using repeated string replacement.
4. `$4` becomes `$10`, then the later replacement of `$1` also changes the prefix of `$10`, producing `$70`.
5. The update fails; the worker enters its uncertain-origination recovery path.

Local reproduction emitted:

```sql
UPDATE dialer_jobs SET status = $1, updated_at = $2, call_id = $3,
processed_at = $4, failure_reason = $5, last_error = $6
WHERE id=$7::uuid AND tenant_id=$8::uuid
AND campaign_id=$9::uuid AND lead_id=$70::uuid RETURNING *
```

Impact: the call may work while its queue record lies. That compromises retry decisions and operator visibility. Duplicate calling is a risk, not something this audit proved happened.

Required fix: correct placeholder transformation in the shared helper, test multi-digit parameters and all affected callers, then reconcile affected jobs using durable call evidence. Do not solve this by deleting ownership predicates or blindly retrying origination.

Acceptance: the generated SQL has exactly `$1` through `$10`; a completed call and its job agree; ambiguous-origination tests show no duplicate call.

## 2. High priority: spoken email confirmation does not open the capture gate

**Confirmed by live transcript, database and failing reproduction.**

The 3:13 call contains a full address readback followed by: “Should I send the rewards card details there?” The caller answers yes. The backend does not recognize that phrasing as its confirmation question.

- `backend/app/domain/services/voice_pipeline/turn_runner.py:105` defines the permitted confirmation wording.
- `_agent_read_back_email`, around line 155, requires both the complete address and that wording.
- The exact observed sentence returns `False` in a local test.
- The account has no persisted email rows in `call_lead_details`; the inspected recent calls have no captured lead-detail rows.

This is not evidence that the tenant's campaign prompt was absent. It is a mismatch between generated conversation and the deterministic confirmation state machine.

Required fix: backend-owned readback/confirmation transitions shared by browser and telephone pipelines, with explicit correction handling. Keep persistence fail-closed until confirmation; do not accept every isolated “yes.”

Acceptance: replay the actual exchange, corrections, interruptions, ambiguous affirmations and cancellation. Save only the fully read-back, confirmed address, with audit fields.

## 3. High priority: the voice agent can promise actions it cannot perform

**Confirmed source capability gap and guard behavior; caller-visible promise observed.**

`backend/app/domain/services/voice_pipeline/action_tools.py:1` explicitly states that live voice has no executor for email delivery, callback scheduling, form submission or controlled transfer. Those tools fail closed. `end_call` is executable.

However, `backend/app/domain/services/llm_guardrails.py:35` mostly detects completed-action claims, not unsupported future commitments. A local check returned:

```text
validate_response('I will send the details by email.', action_results={})
=> (True, None)
```

The observed call promises to send details, although no delivery executor is connected in this runtime. Having Gmail marked Connected in the connectors screen does not establish a voice-to-email execution path.

Important correction to older reports: guard validation **is wired** before TTS in `turn_streamer.py:662`. The defect is incomplete coverage and unavailable execution, not a wholly absent validator.

Required fix: make advertised capabilities match executable capabilities; require durable action evidence before commitments, or explicitly say the address is being collected for human follow-up. Do not simply enable transfer or email flags without delivery, authorization and idempotency.

Acceptance: unavailable actions produce an honest limitation; available actions provide successful/failed tool results; retries cannot duplicate external actions.

## 4. High priority: call-summary prompt and strict schema disagree

**Confirmed by production provider errors and failing reproduction.**

`backend/app/domain/services/call_summary/summarizer.py` asks the model for object entries in `objections` and `action_items`, but `_SUMMARY_SCHEMA_PROPERTIES` around line 102 declares those lists as arrays of strings.

Production evidence on 15 September:

- 17:41:32 UTC: maximum completion tokens reached before a valid document was generated.
- 18:27:36 UTC: `/action_items/0` expected a string but got an object.
- The associated 2:04 and 3:13 calls have no structured summary; the 4:56 call does.

The first error is a separate token-budget failure; the schema contradiction does not explain every summary failure. Strict structured output is not proof that a provider call always succeeds.

Required fix: agree one schema across prompt, validator, storage and UI; size the completion budget for the selected model; use bounded classified retries and a visible failed-summary state. Avoid logging raw generated customer content in provider error details.

Acceptance: adversarial summaries with multiple objections/actions validate; token-limit and schema failures are recoverable or visibly terminal, never silently missing or retried forever.

## 5. High priority: top-up balance silently reads zero usage under RLS

**Confirmed on the live billing screen and by a read-only database reproduction.**

`backend/app/api/v1/endpoints/billing_topups.py:147` acquires a bare pooled connection and calls `compute_minutes_status`. The function touches protected calls and call legs, but the connection is not given tenant context.

Exact production comparison for this account:

```text
without tenant context: allocated=5000, used_minutes=0, remaining_minutes=5000
with tenant context:    allocated=5000, used_minutes=24, remaining_minutes=4976
```

The billing top-up card shows the first result. Dashboard/profile use the second.

Required fix: acquire a tenant-scoped transaction at the endpoint boundary, and test using the real non-BYPASSRLS application role. A tenant_id WHERE predicate alone does not overcome a policy denying all rows.

Acceptance: the top-up balance, quota gate and dashboard agree for this account; pooled connections do not retain another tenant's context.

## 6. Billing also has two competing allocation sources

**Confirmed UI contradiction and source trace.**

The same billing page displays:

- Current Plan: Free Trial, 30 included, 24 used, 6 remaining.
- Top-up card: 5,000 remaining, 0 of 5,000 used.
- Dashboard/profile: 5,000 allocated and 4,976 remaining.

Even after fixing the zero-usage RLS defect, 6 versus 4,976 remains. `backend/app/api/v1/endpoints/billing.py:243` uses the subscription plan's minutes; `minutes_quota.py` uses `tenants.minutes_allocated`.

Required fix: distinguish base-plan entitlement, purchased/manual allocations and authoritative remaining balance, with one reconciliation contract. Do not overwrite the tenant allocation merely to make the labels agree.

Additionally, all 16 current-month real call rows inspected retain `billing_status=none`, which the UI translates to “Not billed.” The quota deliberately includes legacy outbound rows with this value (`minutes_quota.py:87`). This is a misleading status label, **not proof that outbound usage is unmetered**.

Acceptance: entitlement adjustments and top-ups remain intact; every screen explains the same remaining balance and call-accounting state.

## 7. Medium/high: silence handling can interrupt active speech

**Observed in live timing; supported by the monitor's wiring.**

During the 3:13 call, speech continued from a Flux StartOfTurn at 18:25:35 UTC. At 18:25:50 the monitor suppressed a nudge because caller RMS was 1278. RMS later fell below the fixed threshold; the monitor spoke “Still there?” at 18:25:54. Flux did not finalize that utterance until 18:25:56.

`backend/app/domain/services/voice_pipeline/audio_ingest.py:648` resets silence clocks on completed turns/backchannels and a barge event. The acoustic activity check around line 714 can suppress a nudge without refreshing those clocks. The separately updated `_last_caller_activity_monotonic` is not consumed by this monitor path.

This explains a reproducible class of premature nudges at pauses inside a long utterance. It does not establish that every listening complaint has this cause.

Required fix: consistent active-utterance/activity evidence, with proper end-of-speech and noise handling. Simply lowering the RMS threshold risks letting background noise hold calls forever.

Acceptance: long speech, quiet speakers, natural pauses, noisy lines and delayed STT finals neither cause premature nudges nor disable genuine silence termination.

## 8. Medium: interim STT fragments flood the transcript UI

**Confirmed database counts, API behavior and UI mapping.**

| 5a57e2a2 | 2:04 | 17 | 240 | 223 |

`transcript_handler.py:376` persists interim STT with flags. `transcript_service.py:238` returns all JSON turns; the call transcript endpoint exposes them. `Talk-Leee/src/app/calls/[id]/page.tsx:65` and `:422` render the returned array without a canonical-only filter.

Acceptance: the normal transcript shows finalized delivered conversation; diagnostics retain optional event detail. Timestamps are timezone-aware and tested outside UTC.

## 11. Security hardening gap: tenant backup table lacks RLS

`public.tenant_ai_configs_backup_20260907` contains a tenant_id column but has RLS disabled, FORCE RLS disabled and zero policies. The application role has table privileges. This account has zero rows in that table.

## 12. Recording durability and metadata need reconciliation

**Confirmed local-storage path and inaccurate provider field; no loss proved.**

Logs show local recording saves because S3 is not configured. The account's 141 recording rows report `storage_provider=s3`, `status=uploaded`, MIME `audio/mpeg`.

`recording_service.py:683` deliberately uses `s3_bucket=local` and status uploaded for local fallback; its insert does not set storage_provider, allowing the S3 default. The stream endpoint checks the local bucket marker, so the field inconsistency alone does not prove playback fails.

Required follow-up: truthful storage metadata and verified backup/restore/retention for local files. Object-store durability cannot be inferred from the table name or uploaded label.
