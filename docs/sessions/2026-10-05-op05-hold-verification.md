## Verified problems and repair

The actual worker and Redis queue implementation previously treated rejected scheduling rules as new attempts: outside-window/day, daily-cap and concurrency holds called `schedule_retry`, incremented the attempt, then saved a terminal `skipped` database status. Eight of nine new controls failed before the repair; the genuine post-attempt retry control already passed. The shared rejection branch now uses the existing original-payload deferral helper with the existing rule-selected delay. Both genuine cooldown and stale-timestamp cleanup preserve the original attempt; stale cleanup keeps its supported timestamp correction and re-evaluates after one second. The worker commits guarded `retry_scheduled` plus the exact due time before Redis publication, keeping active database ownership. The update binds tenant, campaign, lead, active status and a database attempt no newer than the original payload; it cannot revive a terminal or newer-attempt owner. The existing Redis-ahead pre-answer retry compatibility remains unchanged.

Two additional fault controls showed that a bookkeeping database error after a successful queue handoff entered the generic attempted-call retry path, producing two scheduled payloads and attempt N+1. The final order addresses the boundary directly: failure to commit the durable hold leaves the original inflight payload and publishes no future entry; Redis handoff failure retains the committed active hold and original inflight evidence. A later ancillary lead projection failure cannot create another attempt. Cancellation is not swallowed.

Actual PostgreSQL plus the existing reapers then reproduced two further failures: an aged processing row was released despite its surviving scheduled payload after a denied database projection, and a valid 72-hour hold was released at age 49 hours. Due time now drives the age threshold. Age alone never frees an uncertain job: the existing reaper writes `stuck_reconciliation_required` or `retry_schedule_reconciliation_required` once, preserving active status, attempt and ownership. A future due time is protected; repeated unchanged diagnostic ticks do not produce repeated row/log updates. Authoritative call finalization and explicit cancellation remain the owners of terminal cleanup. This intentionally does not claim automatic recovery of an orphan whose effect/queue evidence is unavailable.

Actual migrated PostgreSQL exposed a second problem: the one-active-job index existed only in historical standalone SQL, outside the complete-schema/Alembic path. `0060_dialer_active_job_owner` (after 0059) now installs the existing active predicate: pending, queued, retry_scheduled, processing, calling. The matching bootstrap block has the same contract. A transaction-scoped writer lock closes the preflight/build race. Existing duplicate jobs cause an actionable migration failure without modifying any job. Existing named invalid, wrong-key, nonunique or unsupported-predicate indexes fail explicitly; valid stronger guards are retained. Downgrade retains the safety index. The historical SQL is marked retired because it automatically cancels siblings and was not executed.

## Scope and rollout limits

This proves application behavior with actual queue code over FakeRedis and actual PostgreSQL, not a real Redis process restart, real PSTN behavior, production migration compatibility, or complete OP05 qualification. Synthetic provider calls are spies only. Existing scheduling windows, daily-cap reset, cooldown delays, paid allowance policy and post-attempt retry policy were not changed. Redis publication then inflight cleanup remains the existing staged handoff; lost publication acknowledgement retains the original inflight evidence.

The stale-cooldown workaround is repaired in this follow-up; batch pacing and other pre-admission paths remain outside this bounded repair. A job with unresolved queue/effect ownership now stays active and carries a database/log reconciliation diagnostic; operators must inspect its exact call/queue evidence before cancelling or otherwise resolving it. This can retain a genuinely orphaned lead slot until reviewed. There is no new reconciliation service, unsafe inferred absence, or automatic provider replay. Native DNC lifecycle persistence remains a separate OP05/OP07 handoff. No full OP05 completion or release approval follows from these results.

Deploy the canonical migration through the normal reviewed process before relying on database uniqueness. A duplicate or incompatible-index failure requires inspection of the existing call/queue evidence; do not execute the historical cancelling script. Code rollback may revert the worker delta while retaining 0060's index; do not drop the invariant as an automatic rollback step.
