## What was wrong and what changed

1. **The saved contact did not reliably retain the evidence that confirmed it.** Current-contact serialization omitted confirmation evidence that additional-contact serialization already kept. Both now retain separate bounded caller identities and revision digests for the value, confirmation and status change. A readback receipt is recorded only when the existing matching completed transport receipt exists. It is not proof that a human heard or understood it. The confirmation contract and model defaults are unchanged.

2. **A corrected recognition could leave the old contact confirmed.** Native same-item revisions now reduce the corrected text against that item's original context and merge only the contact fields it still owns. Independent contact changes, action state and unrelated live facts survive. Empty first finals keep their identity so a later revision can attach to the correct evidence. Traditional capture binds the exact accepted transcript object to its caller order, including queue coalescing and proven duplicate receipts; equal words on separate turns are not treated as the same caller event.

3. **A failed contact revocation could prevent its own retry.** Additional fields such as `email_2` were also rejected by a service that only accepted the primary keys. The existing writer now permits validated additional keys, conditionally updates the previously acknowledged value/evidence, and records successful-write fingerprints only after acknowledgment. A failed revocation blocks its dependent replacement until retry. Manual or independently newer evidence wins. Invalid, clarification and withdrawn states can be saved as explicit null values only when backed by an actual caller-owned transition.

4. **A literal email could bypass the self-contact guard.** A colleague's address could enter through the generic literal parser even when the anchored self-email parser rejected it. The same existing ownership guard now applies to that branch. Direct self statements, business addresses and bare answers remain supported; quoted, negated, reported, action-recipient and third-party addresses are negative controls. This is a bounded parser repair, not a claim of perfect language interpretation.

5. **A durable transcript correction could outlive a failed contact update.** The shared contact read projection now compares versioned value/confirmation/status evidence with the current durable caller transcript. A changed value loses active usability; a changed confirmation loses confirmed status while retaining a still-supported candidate. Original stored evidence remains available for review. Call details, contact details, required-field checks, summary contact facts and the call list use this guard. Malformed proof cannot be treated as legacy confirmation. Genuine legacy rows are explicitly unversioned rather than presented as newly established proof. Manual edits retain their independent authority.

6. **Final transcript failure discarded the only retryable copy.** Final saving now uses one tenant-owned calls/child-transcript transaction, bounded retries, and acknowledgment before memory is cleared. The calls-row lock serializes duplicate finalizers; a completed snapshot fences late incremental writes. Incremental snapshots are taken after the per-call lock is acquired. Native calls now request a coalesced incremental flush, and traditional flushes use the authoritative call/tenant binding even when no knowledge source is configured. A successful deterministic clarification is also recorded through the existing transcript service.

7. **Readers could use an obsolete transcript or summary.** One canonical projection applies valid bound revisions, preserves original audit text, omits retracted speech, and treats corrupt/truncated revisions as unavailable. Existing legacy turn aliases remain supported. Current call snapshots take precedence over historical child rows. Summary revision hashes are versioned, and lead qualification writes now carry the same snapshot fence as summary details. A stale job cannot qualify a lead using a transcript that changed while it was processing.

8. **The Leads panel assigned the wrong meaning to missing data.** Null no longer means that the caller declined. Pending, clarification, invalid, withdrawn, explicit decline and missing evidence have distinct labels. The panel shows value-source and confirmation-source separately; obsolete confirmation is labeled previous. Transcript save completeness is separate from analysis completion. A failed manual save retains the old visible value and the edit error. A blank manual contact edit creates a higher-trust withdrawal instead of a false verified value. Required fields come from the call's actual campaign, and the latest manual review wins across calls.

## Saving and recovery boundaries

Migration `0057_transcript_save_state` adds `unknown`, `partial`, `complete` and `failed` to the existing calls row. Legacy records remain unknown. Complete means that the final transcript snapshot transaction committed; it does not certify transcription accuracy, contact saving, model analysis or delivery of an external action.

Hangup retries the same idempotent contact writer after a successful transcript commit. Recoverable and persistent contact-write failures use the existing contact-followup evidence field, independently of analysis status. If the database cannot accept even a failure note, the system cannot claim that the note was saved.

Failed finalization retains at most 64 call buffers, five minutes and two million characters in the same process. This is bounded retry support, not a durable queue or restart recovery. After a process dies, only previously committed evidence remains. The API exposes the last partial/unknown/failed state and the existing call-review/manual-correction route; it does not reconstruct words that were never stored. If the supported sale requires a stronger durability guarantee, that requirement remains open rather than being implied by these tests.

## Remaining acceptance and rollback

AG06 must verify that queued connector payloads, account identity, external receipts and reconciliation preserve these evidence boundaries. A revision-aware API projection alone does not update an already frozen external payload. Human annotation must measure exact contact accuracy, business qualification precision/recall and correction burden on the approved cohort. Browser-to-API Sales Hub acceptance, actual STT/TTS/PSTN behavior and release checks remain open. Native opt-out durability remains the OP05/OP07 handoff. AG02 retrieval targets and the preserved AG04 semantic failure are unchanged.

Deploy the additive migration before application code that selects the new column. Drain active calls before changing transcript/contact ownership contracts. The migration downgrade deliberately retains the evidence column; rollback must not delete confirmations, revisions, manual edits or receipts. Prefer a forward repair where older code would again expose obsolete confirmation. The migration used a five-second lock timeout on the synthetic database; production lock timing, deployment and rollback have not been exercised.
