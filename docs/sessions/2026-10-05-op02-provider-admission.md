## Reproduced problems and repairs

1. **Flux bypassed the provider allowance.** Both cold and prewarmed sockets connected without the existing `deepgram` guard, while Nova already used it. At configured cap 1, two synthetic Flux connections opened and the guard reported zero. One `_FluxConnection` now owns one permit from before handshake until its shared socket-close task finishes. Stream handoff transfers that same object; it does not acquire a second permit. See `backend/app/infrastructure/stt/deepgram_flux.py:45`, `:495`, `:528`, `:1038`, `:1098`.
2. **Prewarm ownership could be lost.** Repeated same-call prewarm overwrote a socket; a handshake finishing after cleanup repopulated a closed provider. Prewarm now deduplicates the pending handshake, cleanup cancels it and fences late results with a generation, and a stream-adopted socket cannot be cached by a later prewarm waiter. Cancellation of one close waiter leaves the single close task owning its permit until transport close finishes. Installed `websockets` 15.0.1 has 10-second open/close defaults; those defaults were inspected, not retuned.
3. **Strict warmup could report success after a failed Flux connection.** Flux swallowed its connection error. It now propagates to the caller's existing policy. Separately, cancelling `prepare_prewarmed_session` after Flux opened while another warmup was pending skipped created-session cleanup. The actual method reproduced zero cleanup calls; an explicit cancellation branch now awaits the existing session cleanup owner. A cleanup exception is logged, not represented as successful resource release. See `backend/app/domain/services/telephony/prewarm.py`.
4. **Outbound shared admission failed open.** The actual `_on_new_call` method continued to voice setup with missing/error Redis. It now passes `fail_closed=True` and records the refusal reason. This check remains **after provider Answer and before voice setup**. It does not prevent outbound ringing or establish a pre-origination global reservation. Inbound's existing pre-Answer strict admission remains intact. See `backend/app/domain/services/telephony/lifecycle.py:3659`.
5. **Redis claim/reconciliation had observable gaps.** SADD/SCARD committed before SET of the lease; reconciliation could remove that new member and admit a second call at cap 1. A stale EXISTS reply could also remove a freshly renewed member. Acquisition is now one parameterized Lua operation on the existing keys; reconciliation atomically rechecks before removing a candidate. See `backend/app/domain/services/global_concurrency.py:64`, `:94`, `:341`.
6. **Failed same-ID acquisition could delete a prior live lease.** Failure/cancellation cleanup unconditionally released by call ID. New claims use a unique acquisition token in the existing lease value, and cleanup compare-deletes only that token. Idempotent existing claims retain prior ownership. A restored existing set member gets a non-attempt marker; heartbeat also revokes stale acquisition-cleanup authority. An existing lease whose set membership was lost is restored and counted even when that reveals occupancy above cap; further new admission is refused. Legacy pod-only values remain valid. See `global_concurrency.py:84`, `:147`, `:228`.
7. **A copied watchdog snapshot could recreate an ended slot.** A process-local maintenance lock now orders each refresh against release. Under that lock the watchdog checks both the exact currently registered session object and the existing ended marker. It skips removed/setup-failed/ownership-lost sessions, while retaining missing-key recovery for a genuinely live session. An already-entered refresh finishes before normal/strict release. Refresh is bounded to one second; the existing one-second release deadlines remain. This is local ordering, not a claim of cross-process fencing or resolution of transport-ambiguous delayed commands. See `lifecycle.py:65`, `:84`, `:1036`, `:2323`, `:4959`, `:5557`.

## Public ownership boundary

No HTTP endpoint directly exposes the global `release_lease` or `refresh_lease` functions. The telephony API imports global capacity only for read-only status. Global mutations are internal admission, watchdog and proof/terminal lifecycle operations; random call IDs are not treated as authorization.

The separate public tenant lease routes `/telephony/sip/runtime/concurrency/leases/{lease_id}/release` and `/heartbeat` derive tenant from authenticated `CurrentUser`, require a tenant, apply scoped RLS context, and call limiter SQL with `WHERE tenant_id = $1 AND id = $2`. A new actual ASGI route + actual limiter test uses synthetic auth and an SQL seam: foreign release and heartbeat return 404 without changing the owner's lease/counter; forged tenant input returns 422; owner release succeeds. This is not new real-PostgreSQL RLS proof.

Raw `/hangup/{call_id}` uses `_require_call_control` and `_verify_call_ownership`: the latter reads the call's owning tenant by provider identity and compares it with the authenticated tenant, denying unknown/foreign calls. A new actual-handler control proves foreign hangup is rejected before provider or settlement methods. Trusted internal service-token callers explicitly have cross-tenant system authority. The tenant `/calls/{id}/hangup` path additionally selects `calls` by both durable ID and tenant. No auth/permission implementation was changed here.

Relevant existing code: `backend/app/api/v1/endpoints/telephony_concurrency.py:184`, `:229`; `backend/app/domain/services/telephony_concurrency_limiter.py:422`, `:472`; `backend/app/api/v1/endpoints/telephony_bridge.py:2458`, `:2644`; `backend/app/api/v1/endpoints/calls.py:567`.
