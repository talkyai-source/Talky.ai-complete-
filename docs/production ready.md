## 2 What production ready means

A feature is ready for paid use only when its visible promise, backend behavior, failure handling and operating evidence agree for a defined customer profile. A profile identifies use case, direction, region/language, provider/model/voice, knowledge version, connectors, trunk/carrier and supported limits. Evidence for one profile cannot silently approve every other option.

| Requirement | Evidence required |
|---|---|
| Truthful customer experience | No false success, fabricated invoice field, demo operation presented as real, or unavailable action promised by the agent |
| Correct and authorized effects | Correct tenant, caller ID, recipient and destination account; permission checked server-side; replay cannot duplicate an external effect |
| Durable usable results | Confirmed contacts, reviewed business evidence, call outcomes and action/payment receipts survive the declared failure/recovery contract and are shown consistently |
| Failure visibility | Unknown, pending, declined, unavailable and failed states remain distinct; a customer or operator has a documented next step |
| Conversation quality | Representative real telephone calls satisfy the agreed comprehension, contact capture, interruption, closure and listening rubric |
| Financial correctness | Purchase interval, price, entitlement, usage policy, invoice, refunds and cancellation reconcile to authoritative records |
| Operational support | Alerts reach a person, backup restoration is demonstrated, resources clean up, and the tested compatible release can recover safely |
| Customer value | A controlled pilot shows useful outcomes and acceptable human correction/support effort, with costs included and no invented uplift |

Work status moves through `planned` → `in_progress` → `candidate_verified` → `release_verified` → `pilot_validated` → `closed`. Use `blocked`, `failed` or `contained_not_complete` when appropriate. A documentation-only claim correction can close after deployed content verification; a call feature cannot close on that lighter standard. Record which evidence standard applies to each item.

Every closure record must contain the baseline finding, exact changes or validation-only disposition, commit/build, relevant environment/configuration, test IDs and artifacts, observed result, reviewer and release/pilot reference when needed. Never replace the original failure evidence with a later success. Unknown provider effects remain unresolved until independently reconciled or recorded as unresolved under an honest customer-facing workflow.

## 4 Commercial and customer journey work

### CP01 Honest discovery claims and reliable enquiries

**Scope and classification:** confirmed false-success defect F02; evidence gap F01; decisive form accessibility F38. The contact form waits 1.5 seconds, clears the draft and reports success without a request or stored receipt. Numeric homepage claims have no reviewed measurement provenance; this does not prove the numbers false. Evidence: `Talk-Leee/src/components/home/contact-section.tsx:39`, `Talk-Leee/src/app/contact/page.tsx:15`, `Talk-Leee/src/components/home/home-lazy-sections.tsx:312`, `Talk-Leee/src/components/home/stats-section.tsx:8`.

**Bounded implementation:**

1. Immediately remove the timer-based sent state. Default containment is an accurately labelled contact-email link with explicit copy/open-mail behavior; opening a mail application is not proof of sending. Keep any entered draft until the user chooses to clear it.
2. If the existing offer requires a website submission form, connect it to one existing supported intake destination only after its owner and retention policy are known. The server returns a durable request/acceptance identifier; sending email alone must not manufacture an intake record. Reuse existing delivery infrastructure where its contract fits. Apply bounded size validation, existing rate limiting and safe rendering; do not build a CRM or support desk.
3. Use a stable request identity for double-click/network retry. A timeout after possible acceptance displays an unresolved state and allows checking/retrying that identity. Preserve the draft on known failure; distinguish accepted by intake from delivered/read by a person.
4. Inventory only the claims already present on the public pages and offer: latency, scale, completion, uplift, customer logos and regulated-use assertions. Link each retained factual claim to dated evidence with its population, definition and permission where relevant. Remove or clearly label an unproven target. The operations/quality packages produce any future measurements; this package does not invent them.

**Dependencies / owner:** customer-operations owner for a reachable intake; existing email/durable-receipt service if the form is retained; product marketing owner for claim truth; privacy work for permitted intake data. Accountable: frontend product lead, with customer operations and product marketing reviewers.

**Acceptance:** positive — a designated synthetic enquiry has one saved receipt and reaches the agreed intake, or the contained page offers an honest functioning contact alternative with no sent claim. Negative — malformed/oversized input and unsupported destinations are rejected; the form is usable by keyboard with named controls. Failure — double-click, timeout after acceptance, service refusal, reload and retry never lose an unsent draft or create a fabricated success; one accepted identity cannot create duplicate intake records. Every retained numerical/customer claim has evidence, or is absent from the sold offer.

**Rollback and reconciliation:** roll back a broken form to the honest email alternative, never the fake success timer. Preserve accepted records and pending statuses. Historical browser-only submissions cannot be reconstructed from nonexistent receipts; do not claim a recovered backlog. If an actual customer reports a lost enquiry, record and handle it through the supported intake.

**Closure evidence:** before/after rendered page, focused form/request tests, a sanitized receipt and intake observation, failure-path trace, and a short claim-to-evidence list. Record F02 as completed only if real intake works; otherwise record containment explicitly.

### CP03 Recoverable billing webhooks without duplicate financial effects

**Scope and classification:** reproduced ordinary webhook retry loss F10; preservation/acceptance of monthly and top-up/refund flows F07/F09. A claimed event whose subscription/invoice handler fails is treated as a duplicate on retry. Claim-storage failure deliberately processes without a durable claim. These boundaries can lose updates or repeat secondary work; they are not proof of double charging. Invoice upsert and top-up ledger uniqueness already protect specific effects. Evidence: `backend/app/domain/services/billing_service.py:465`, `:480`, `:500`, `:507`; `backend/database/migrations/20260610_processed_webhook_events.sql:7`; `backend/app/domain/services/topup_service.py:202`; saved `docs/sessions/artifacts/2026-10-02-maturity-billing-repro.py` and `.json`.

**Bounded implementation:**

1. Reuse `processed_webhook_events` with a narrow additive processing/completion record and ownership metadata only where needed. Existing rows prove an earlier claim, not necessarily completed business work. Preserve that ambiguity for reconciliation; do not backfill every legacy row as successful or delete them all to replay.
2. Make the signed event identifier the stable deduplication identity. Only a completed event may return the ordinary completed-duplicate acknowledgement. A concurrent/in-progress or transiently failed event must remain durably resumable, or the HTTP response must cause provider redelivery. Do not acknowledge durable completion merely because another handler began work.
3. Fail closed on unavailable receipt storage: return a retryable non-success before financial/subscription processing. Preserve existing invoice-ID upserts, top-up provider-event uniqueness and atomic ledger mutations. Where handler effects are database-only, prefer one existing database transaction; where not, retain explicit recoverable boundaries rather than claiming an external action joins that transaction.
4. Process duplicate and unordered subscription events without reverting newer authoritative state. Use provider subscription/invoice identity and the existing current-state retrieval contract where necessary; do not assume arrival order or invent a timestamp rule that makes unrelated objects comparable.
5. Separate billing state completion from receipt-email delivery. A notification failure must be observable and recoverable without repeating a credit/reset/cancellation. Reuse existing durable delivery machinery only after verifying its acknowledgement/idempotency contract. An uncertain external send remains uncertain and must not be blindly resent.
6. Add a bounded reconciliation procedure for legacy claimed events, stale work and provider/local divergence. Inspect provider event/object and ledger evidence first; replay only idempotent work whose status is established. Preserve a record of decisions and resulting differences.

**Closure evidence:** migration proof, focused handler/ledger tests, concurrent real-database results, signed test-mode provider replay/order results, recovery traces at each injected boundary, and a reconciled event sample. Existing `test_billing_topup_webhook_routing.py`, `test_topup_service.py` and `test_billing_plan_change_preserves_topup_minutes.py` remain regression anchors.

Avoid counting the same benefit twice or using gross revenue as profit. Separately reconcile platform telephony/STT/LLM/TTS/storage/retry/support/refund cost against provider records; the in-memory cost telemetry alone is insufficient. Record assumptions and sensitivity to longer calls, more retries and support time. This is measurement for the current offer, not a new pricing engine or analytics feature.

Exit evidence: customer-journey and profile gates met, observed outcomes acceptable to the agreed buyer criteria, meaningful support/cost evidence, corrected material pilot defects with revalidation, and a transparent offer the team can operate. No numeric ROI or conversion claim is published unless supported by that evidence.

### Stop conditions and recovery

Stop new affected work and keep existing calls safe if there is wrong-tenant access, unauthorized/wrong-recipient origination, a false completed financial/external action, lost confirmed evidence, failure to enforce an explicit opt-out, uncontrolled spend/admission, or a critical privacy/security failure. Stop new affected admission immediately; preserve available receipts and evidence without delaying containment. If storage is unavailable, record the persistence gap and use the existing safe recovery path. Do not wipe or replay work to make the dashboard look clean. Scope containment to the affected profile, tenant or capability only when isolation is proven; otherwise stop the broader admission path.

For quality targets, a failed profile does not expand beyond controlled testing until corrected and rerun. For uncertain actions/payments, reconcile against the exact provider account/event before another effect. For infrastructure incidents, follow the tested compatible recovery procedure and prove health plus the affected customer journey before reopening admission. The operational owner records who made the decision and why.

### Lifting the feature freeze

The product owner may record full-plan completion only when every mapped finding has an evidence-backed disposition, every feature promised or enabled for paid customers satisfies its applicable gates, and no feature marked contained/blocked is falsely described as finished. All residual operational limitations must be documented in the offer and operating procedure. Full-plan completion and feature-freeze exit are forbidden while any in-scope item remains blocked, failed or contained_not_complete, or has an unrun required gate. Only an explicit user scope revision removes that obligation. A reviewed validation-only/no-change disposition for an architecture risk is a valid closure when its rationale and evidence are recorded; it is not containment. A successful narrow pilot alone does not release the global freeze.

A per-feature closure record must show what a paying customer can now do, what happens on failure, what is saved, what the operator can recover, and which evidence proves it. Findings resolved through a verified existing implementation are valid closures. Unavailable accounts, unrun tests, unreviewed contracts or unchecked production state are not. Sustained-production maturity can only be earned through subsequent evidence, not granted by a release meeting.

## 10 Evidence and execution checklist

Use [execution-tracker.json](production-readiness/execution-tracker.json) as the status ledger for this plan; keep the frozen baseline files unchanged. The plan describes the work, and the tracker records progress and evidence. Neither creates a second runtime configuration system. For each work package:

1. Assign the responsible person and independent reviewer to the listed roles; identify overlapping files, dependencies and data changes.
2. Reproduce the confirmed issue, or document the bounded proof required for an unverified risk. Record the expected customer/backend outcome before changing code.
3. Implement the smallest repair to the existing path. Add a schema field/table only when durable state requires it; review migration and reconciliation separately from UI behavior.
4. Exercise positive, negative, duplicate, out-of-order and interruption/crash cases applicable to the change. Preserve existing tenant, authorization, DNC and billing/action fences.
5. Record focused results, then integrate and run the established candidate checks. Cite the exact commit and configuration, not just a branch or test count.
6. Review rollout, compatibility, rollback/code-forward and any existing-data reconciliation. Never blindly replay old webhook/action records or erase receipts.
7. Complete required designated-account and deployed acceptance; record blocked inputs without implying success. Link the independent destination/database evidence.
